# Internationalization (i18n) Documentation

This document explains how the Next.js internationalization (i18n) feature is implemented in this application.

## Overview

The application uses Next.js App Router with locale-based routing to support multiple languages. All routes are prefixed with a locale code (e.g., `/en`, `/es`, `/zh`), and the middleware automatically handles locale detection and redirection.

## Supported Locales

The application currently supports three locales:

- **en** - English (default)
- **es** - Spanish (Español)
- **zh** - Chinese (中文)

These are defined in `middleware.ts`:

```typescript
export const locales = ['en', 'es', 'zh'] as const;
export const defaultLocale: Locale = 'en';
```

## Architecture

### File Structure

The i18n implementation follows this structure:

```
app/
  ├── layout.tsx                    # Root layout (pass-through)
  └── [locale]/                      # Locale-based routing
      ├── layout.tsx                 # Locale-specific layout
      └── [all pages and routes]    # All pages nested under locale

middleware.ts                        # Locale detection and routing
lib/
  └── i18n.ts                       # Translation utilities
messages/
  ├── en.json                       # English translations
  ├── es.json                       # Spanish translations
  └── zh.json                       # Chinese translations
```

### Locale-Based Routing

All application routes are nested under the `[locale]` dynamic segment in the App Router. This means:

- `/` → Redirects to `/en/` (or user's preferred locale)
- `/en/products` → English products page
- `/es/products` → Spanish products page
- `/zh/products` → Chinese products page

The locale is always present in the URL path, ensuring consistent routing and SEO-friendly URLs.

## Middleware

The middleware (`middleware.ts`) is responsible for:

1. **Locale Detection**: Determines the user's preferred locale through multiple strategies
2. **Automatic Redirection**: Redirects requests without a locale prefix to the appropriate locale-prefixed URL
3. **Static File Exclusion**: Skips processing for static files, API routes, and Next.js internals

### Locale Detection Strategy

The middleware uses a priority-based detection system:

1. **URL Path** (highest priority): If the pathname already contains a locale (e.g., `/en/products`), that locale is used
2. **Accept-Language Header**: Parses the browser's `Accept-Language` header to detect preferred language
3. **Cookie**: Checks for a `NEXT_LOCALE` cookie if set
4. **Default Locale**: Falls back to `en` if no locale can be determined

### Middleware Configuration

The middleware matcher excludes:
- API routes (`/api/*`)
- Next.js static files (`/_next/static/*`, `/_next/image/*`)
- Favicon and image files (`.ico`, `.png`, `.jpg`, `.jpeg`, `.svg`, `.webp`, `.avif`)

## Translation System

### Translation Files

Translations are stored as JSON files in the `messages/` directory. Each locale has its own file:

- `messages/en.json` - English translations
- `messages/es.json` - Spanish translations
- `messages/zh.json` - Chinese translations

### Translation Structure

Translations use a nested object structure with dot-notation keys:

```json
{
  "common": {
    "nav": {
      "home": "Home",
      "products": "Products"
    },
    "buttons": {
      "addToCart": "Add to Cart"
    }
  },
  "home": {
    "title": "Welcome"
  }
}
```

### Using Translations in Components

#### Server Components

In Server Components (async components), use `getTranslations()` and `getNestedTranslation()`:

```typescript
import { getTranslations, getNestedTranslation } from 'lib/i18n';
import { Locale } from 'middleware';

export default async function Page({
  params,
}: {
  params: Promise<{ locale: Locale }>;
}) {
  const { locale } = await params;
  const t = await getTranslations(locale);

  return (
    <div>
      <h1>{getNestedTranslation(t, 'home.title')}</h1>
      <button>{getNestedTranslation(t, 'common.buttons.addToCart')}</button>
    </div>
  );
}
```

#### Translation Functions

**`getTranslations(locale: Locale)`**

Loads and returns all translation messages for a given locale. If the locale file fails to load, it falls back to the default locale (`en`).

**`getNestedTranslation(messages: Messages, key: string)`**

Retrieves a translation value using dot-notation (e.g., `'common.nav.home'`). Returns the key itself if the translation is not found.

**`createTranslator(locale: Locale)`**

Creates a translation function for a specific locale. Returns an async function that takes a key and returns the translated string.

### Translation Utilities

The `lib/i18n.ts` file provides several utility functions:

- **`getLocaleFromPath(pathname: string)`**: Extracts the locale from a pathname
- **`removeLocaleFromPath(pathname: string)`**: Removes the locale prefix from a pathname
- **`getTranslations(locale: Locale)`**: Loads translations for a locale
- **`getNestedTranslation(messages: Messages, key: string)`**: Gets a nested translation value
- **`createTranslator(locale: Locale)`**: Creates a translator function

## Language Switcher

The application includes a `LanguageSwitcher` component (`components/layout/language-switcher.tsx`) that allows users to switch between languages.

### How It Works

1. Extracts the current locale from the URL pathname
2. Provides a dropdown select with all available locales
3. When a locale is selected, updates the URL by replacing the locale segment while preserving the rest of the path

Example:
- Current URL: `/en/products/item-123`
- User selects Spanish
- New URL: `/es/products/item-123`

## Layout Structure

### Root Layout (`app/layout.tsx`)

The root layout is a simple pass-through component that renders its children. This is necessary because Next.js requires a root layout.

### Locale Layout (`app/[locale]/layout.tsx`)

The locale-specific layout:
- Receives the `locale` parameter from the route
- Sets the `lang` attribute on the `<html>` element
- Renders the navigation bar and main content
- Applies global styles and fonts

## Adding New Translations

### Adding a New Translation Key

1. Add the key to all locale files in `messages/`:

**`messages/en.json`**:
```json
{
  "common": {
    "newKey": "New Translation"
  }
}
```

**`messages/es.json`**:
```json
{
  "common": {
    "newKey": "Nueva Traducción"
  }
}
```

**`messages/zh.json`**:
```json
{
  "common": {
    "newKey": "新翻译"
  }
}
```

2. Use it in your component:
```typescript
{getNestedTranslation(t, 'common.newKey')}
```

### Adding a New Locale

1. Add the locale code to `middleware.ts`:
```typescript
export const locales = ['en', 'es', 'zh', 'fr'] as const;
```

2. Create a new translation file:
```
messages/fr.json
```

3. Add the locale name to the language switcher:
```typescript
const localeNames: Record<Locale, string> = {
  en: 'English',
  es: 'Español',
  zh: '中文',
  fr: 'Français',
};
```

## Best Practices

1. **Always use the locale parameter**: When creating pages, always accept and use the `locale` parameter from `params`
2. **Consistent key naming**: Use a consistent naming convention for translation keys (e.g., `common.nav.home`, `common.buttons.addToCart`)
3. **Fallback handling**: The translation system automatically falls back to the default locale if a translation is missing
4. **Type safety**: Use the `Locale` type from `middleware.ts` for type safety
5. **URL preservation**: When switching languages, the path after the locale is preserved, maintaining the user's navigation context

## Technical Details

### Locale Detection Flow

```
Request → Middleware
  ↓
Check if locale in path?
  ├─ Yes → Continue
  └─ No → Detect locale
      ├─ Check Accept-Language header
      ├─ Check NEXT_LOCALE cookie
      └─ Use default locale
  ↓
Redirect to /{locale}{pathname}
```

### Translation Loading

Translations are loaded dynamically using ES6 dynamic imports:

```typescript
const messages = await import(`../messages/${locale}.json`);
```

This enables code splitting and ensures only the required translation files are loaded.

### SEO Considerations

- Each locale has its own URL, improving SEO
- The `lang` attribute is set on the HTML element for each locale
- Locale-specific metadata can be set in page components

## Troubleshooting

### Translations Not Showing

1. Verify the translation key exists in all locale files
2. Check that the locale parameter is being passed correctly
3. Ensure `getTranslations()` is awaited in async components
4. Check the browser console for import errors

### Locale Not Detected

1. Verify the locale is in the `locales` array in `middleware.ts`
2. Check that the Accept-Language header format is correct
3. Ensure the middleware matcher is not excluding the route

### Redirect Loops

If experiencing redirect loops:
1. Check that static files and API routes are properly excluded in the middleware matcher
2. Verify the middleware is not processing its own redirects
